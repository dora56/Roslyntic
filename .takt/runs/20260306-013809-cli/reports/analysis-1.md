## 1. 分析の観点

以下の5観点でギャップを検出する。

1. **説明されていない現象**: 事実は述べているが「なぜそうなのか」が不明
2. **検証されていない仮説**: 推測が事実として扱われている
3. **欠損している定量データ**: 主張に対して数値の裏付けがない
4. **新たに出現した概念**: 調査中に出てきた用語・概念で深掘りが必要なもの
5. **比較の欠落**: 片方のデータしかなく対比ができていない

## 2. 主要な発見の整理

### 2-1. Roslyntic コードベースの現状

**発見**: Roslyntic は現時点で完全なスケルトン段階。`Program.cs` が 3 行（`Console.WriteLine("Hello, World!")`）のみ。PackageReference はゼロ件。OTel 関連コード・ネットワーク通信コードは一切存在しない。

**重要性の位置づけ**: この調査結果の価値は「現状の問題発見」ではなく「設計フェーズでの意思決定ガイダンス」にある。調査対象が実装前のプロジェクトであるため、全ての外部調査（OTelパターン、ネットワークポリシー）は将来の実装に向けた設計根拠として機能する。

### 2-2. OTel × CLI ツール採用パターン（外部調査）

**発見**:
- 静的解析CLIで OTel を採用しているプロジェクトは少数（Semgrep が唯一の実質的採用例）
- 採用パターンの主流は「環境変数 or CLIフラグによる opt-in」（`OTEL_EXPORTER_OTLP_ENDPOINT` 未設定時は完全無効）
- 短寿命プロセス特有の問題として「Flush タイミング」が確認済み（`IHost.Dispose()` または `ForceFlush()` で解決可能）
- .NET OTel SDK の合計パッケージサイズ: ≒1.36 MB（3パッケージ）
- Semgrep の教訓: OTel を必須依存関係にすると、opt-in 機能でも全ユーザーに影響が出る（Issue #10408 未解決）

**Roslyntic への適合性**: 環境変数 `OTEL_EXPORTER_OTLP_ENDPOINT` による完全 opt-in は「no telemetry by default」制約と完全に両立する。STDOUT を汚染せず、SARIF 出力にも影響しない。

### 2-3. ネットワーク通信ポリシー（外部調査）

**発見**:
- 業界標準の解釈: 「no network calls」= **分析ランタイム時のアウトバウンド通信禁止**
- ビルド時 NuGet restore は「事前工程」として分類されており、`dotnet restore` 済みを前提とするツールが多い
- MSBuildWorkspace 自体はネットワーク通信しない（パッケージ未キャッシュ時に NuGet 復元トリガーが発生する可能性あり）
- 類似ツールとの差別化: SonarScanner がサーバー必須なのに対し、Roslyntic のローカル完結 SARIF 出力はエアギャップ CI 環境での競争優位になる

### 2-4. ADR の網羅確認

| ADR | 内容 | OTel/ネットワーク関連 |
|---|---|---|
| ADR-0001 | 出力コントラクト（SARIF/JSON、no network、no telemetry） | 直接言及あり |
| ADR-0002 | SARIF 出力戦略（最小フィールド、決定論的ソート） | OTel/ネットワークへの言及なし |
| ADR-0003 | プラグイン安全モデル（プロセス分離、フェーズ2+） | OTel/ネットワークへの言及なし |

## 3. ギャップの特定と評価

### ギャップ A: .NET OTel SDK 初期化コストの実測値なし

**内容**: `data-otel-patterns.md` は CLI ツールへの影響を「数十ms 程度で無視できるレベルと推定される」と記載しているが、これは推測であり実測値の裏付けがない。Go や ASP.NET のベンチマーク（-15% RPS）は引用できているが、CLI の短寿命プロセス + .NET のゼロから起動するシナリオの実測値は未発見。

**重要度**: 低
**理由**: 静的解析ツール（`MSBuildWorkspace` のソリューションロードで数秒〜数十秒かかる）の文脈では、数十ms のオーバーヘッドは相対的に小さい。設計判断を覆す可能性は低い。公開ベンチマークが存在しないことも調査ドキュメントに正直に記載されている。
**判断**: 追加調査不要。推測である旨を明示して記録すれば十分。

---

### ギャップ B: ADR-0001 の「no network calls」スコープがビルド時を明示していない

**内容**: ADR-0001 は「Local-only execution: no network calls」と定めているが、ビルド時（NuGet restore）に関する言及がない。MSBuildWorkspace が暗黙的に NuGet restore をトリガーする可能性があり、これが「no network calls」違反に当たるかどうかが不明確。

**重要度**: 中
**理由**: エアギャップ環境での CI/CD 実行時に予期しないネットワーク待機タイムアウトが発生するリスクがある（data-network-policy §4 に業界事例あり）。ただし「事前 `dotnet restore`」の前提を明示することで解決できる問題であり、ADR の改定を必要とするが設計変更は不要。
**追加調査必要か**: 不要。既存データから対策を整理可能。

---

### ギャップ C: ADR-0003（プラグインワーカープロセス）と OTel コンテキスト伝播

**内容**: ADR-0003 は Phase 2+ でプラグインを「独立したワーカープロセス」で実行する設計を定めている。将来的に OTel を opt-in で導入した場合、メインプロセスの OTel コンテキスト（トレース/スパン）をワーカープロセスへ伝播させる必要が生じる。これは IPC 設計に影響する可能性があるが、今回の調査では未検討。

**重要度**: 低（Phase 2 以降の話であり、現時点では MVP 実装に非該当）
**判断**: 追加調査不要。「将来的な留意事項」として記録する。

---

### ギャップ D: MSBuildWorkspace の NuGet restore トリガーの実際の動作

**内容**: `MSBuildWorkspace.OpenSolutionAsync()` が NuGet restore を暗黙的にトリガーするかどうかは、実際にコードを実行して検証しないとわからない。Web 調査では「パッケージがキャッシュ済みなら発生しない」という理解に留まっており、「パッケージ未キャッシュ時に自動ダウンロードするかどうか」が未確認。

**重要度**: 低
**理由**: 対策は既に特定されている（事前 `dotnet restore` 必須、または `EnableNuGetPackageRestore=false` 設定）。実際の動作確認はローカル実行が必要で Web 調査では追加情報を得られる見込みが低い。
**判断**: 追加調査不要。「実装時に検証すべき項目」として記録する。

## 5. 全体サマリー

### 5-1. 現時点での発見サマリー

**Roslyntic コードベース（内部）**:
- OTel 関連コード・ネットワーク通信コード: **ゼロ**（スケルトン段階）
- PackageReference: **ゼロ**（`Roslyntic.Core` 等の主要プロジェクト .csproj は未作成）
- 「no network calls」の ADR-0001 定義: **ランタイム時のアウトバウンド通信禁止**と解釈すべき（ビルド時スコープは明文化が必要）

**OTel 採用パターン（外部）**:
- CLI ツールでの OTel 採用は少数派。Semgrep（opt-in `--trace`）・Docker CLI（環境変数）が代表例
- .NET での推奨パターン: `OTEL_EXPORTER_OTLP_ENDPOINT` 環境変数未設定時に SDK 初期化をスキップ
- 短寿命プロセスの Flush 問題: `using var host = builder.Build()` による自動 Dispose で解決可能
- Semgrep の失敗から学ぶ教訓: OTel を **必須依存関係にしない**（条件付き参照またはビルドフラグで分離）

**ネットワークポリシー比較（外部）**:
- Roslyn/StyleCop: 完全オフライン（ネットワーク通信なし）
- SonarScanner: サーバー必須（Roslyntic と対極的設計）
- Semgrep: デフォルトで複数通信（組み合わせフラグで無効化可能）
- MSBuildWorkspace: パッケージキャッシュ済みなら通信なし（事前 `dotnet restore` を前提条件として明示すべき）

---

### 5-2. 発見の整理

#### OTel 採用に関する推奨方針

| 判断ポイント | 推奨 |
|---|---|
| デフォルト動作 | OTel 完全無効（`OTEL_EXPORTER_OTLP_ENDPOINT` 未設定時） |
| opt-in 方法 | 環境変数 `OTEL_EXPORTER_OTLP_ENDPOINT` を設定するだけで有効化 |
| シグナル | Traces + Metrics を優先（Logs は NDJSON で既にカバー） |
| Flush 保証 | `using var host = builder.Build()` パターン必須 |
| パッケージ依存 | 本番ビルドに OTel SDK を常時含めない（条件付き参照 or 機能フラグ） |
| STDERR 汚染対策 | `OTEL_LOG_LEVEL=none` または OTel 自己テレメトリの明示的無効化 |
| 制約との整合性 | ✅「no telemetry by default」・「STDOUT 汚染なし」・「決定論的出力」すべてと両立 |

#### ネットワークポリシーに関する推奨方針

| 判断ポイント | 推奨 |
|---|---|
| ADR-0001 スコープの明確化 | 「ランタイム中のアウトバウンド通信禁止」と明文化（ビルド時除外を明示） |
| MSBuildWorkspace の NuGet 通信 | 実行前提として「`dotnet restore` 済み」をドキュメントに必須記載 |
| NuGet 自動復元の制御 | `EnableNuGetPackageRestore=false` または `--no-restore` の適用を検討 |
| バージョンチェック | 実装しない（SARIF の `tool.driver.version` に埋め込むだけで十分） |
| エアギャップ対応 | 事前 NuGet キャッシュ + スタンドアローン実行ファイル配布のガイドを提供 |
