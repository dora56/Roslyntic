### 主要な発見

**コードベースの現状（内部スキャン）**
- Roslyntic は完全スケルトン段階。OTel・ネットワーク通信コードともにゼロ
- `Roslyntic.Core` 等の主要プロジェクトの `.csproj` は未作成
- ADR-0001 の「no network calls」はランタイム時のアウトバウンド通信禁止と解釈すべきだが、**ビルド時スコープが明文化されていない**（中程度のギャップ）

**OTel採用パターン（外部調査）**
- CLI での OTel 採用は少数派。推奨パターンは `OTEL_EXPORTER_OTLP_ENDPOINT` 環境変数による完全 opt-in
- 短寿命プロセスの Flush 問題は `IHost.Dispose()` で解決できる（確立した解決策あり）
- Semgrep の失敗教訓: OTel を**必須依存関係にしない**こと（条件付き参照必須）
- 「no telemetry by default」・「STDOUT汚染なし」・「決定論的出力」すべてと両立可能

**ネットワークポリシー比較（外部調査）**
- 業界標準の解釈: 「no network calls」= ランタイム中のアウトバウンド通信禁止（ビルド時 NuGet restore は除外）
- MSBuildWorkspace: パッケージキャッシュ済みなら通信なし（`dotnet restore` 前提の明示が必要）
- Roslyntic のローカル完結 SARIF 出力は SonarScanner と対極的でエアギャップ CI での競争優位
