# 探索的テスト計画 — Roslyntic MVP

## リスク整理

### 実装未完成の全体像

`Program.cs` はスタブ（"Hello, World!"のみ）。`Roslyntic.Core`・`Roslyntic.Rules` のコアパイプラインはこれから実装される。既存ユニットテストは個別コンポーネント（Calculator / Classifier / Sorter / Serializer）のみをカバーし、**パイプライン結合・出力ストリーム制約・実ワークスペース動作は一切カバーしていない**。

---

## P1/P2 リスク候補の特定

| 優先度 | リスク領域 | 根拠 |
|--------|-----------|------|
| **P1** | STDOUT 汚染（機械可読性破壊） | AGENTS.md「non-negotiable contract」。MSBuildWorkspace がデフォルトで STDOUT に診断メッセージを出力する既知のリスク。スタブ `Console.WriteLine` の残存リスクも高い |
| **P1** | End-to-End 決定論性の欠如 | ADR-0001 の核心。プロジェクト列挙順序・HashSet/Dictionary のイテレーション順序・非同期スケジューリングにより byte-identical 保証が崩れる |
| **P1** | 終了コード契約の破綻 | `0/1/2` の区別が CI ゲーティングの基盤。未捕捉例外・部分的ロード失敗が exit 1 を誤生成するリスク |
| **P1** | AGARCH0001 セマンティクス検出精度 | ユニットテストなし。依存種別（継承/属性/呼び出し）の未検出・テストプロジェクトへの誤検知が想定される |
| **P2** | AGCOMP0001 実コードの未カバー構文 | ユニットテストは手書き構文のみ。`switch` 式・null 条件演算子・ローカル関数等のカウント仕様が不明確 |
| **P2** | SARIF rules セクションの不完全性 | `docs/rules.md` は `shortDescription`・`fullDescription`・`helpUri`・`properties.category` を要求。テストは `id` のみ確認 |
| **P2** | CLI エラーハンドリング | 不正パス・欠損 SDK・解析不能プロジェクトへの応答未検証 |

## セッションチャーター

### セッション 1 — STDOUT 汚染 / 出力ストリーム分離

**対象:** `roslyntic check <sln>` の STDOUT／STDERR 分離  
**テスト観点:**
- STDOUT が常に JSON パース可能か（任意の実行条件下で）
- MSBuildWorkspace の診断メッセージが STDOUT に漏れていないか
- 例外スタックトレース・ログが STDOUT に混入しないか
- `--log-file` 指定時に STDOUT が影響を受けないか

**終了条件:** 以下のすべてで `JsonDocument.Parse(stdout)` が成功すること
- 正常サンプル解析
- ビルドエラーを含むプロジェクト解析
- 存在しないパスを引数に渡した実行

**タイムボックス:** 60 分  
**実施担当:** 実装者本人（実装直後に実施）

---

### セッション 2 — 決定論性（同一入力→byte-identical 出力）

**対象:** end-to-end の決定論性保証  
**テスト観点:**
- 同一 `.sln` を 10 回実行し、全出力が byte-identical か
- プロジェクト参照の追加順を変えたとき SARIF 結果順序が変わらないか
- `results` 配列のソート順が `path → startLine → startColumn → ruleId` に厳密に従うか
- ルール（AGARCH0001 / AGCOMP0001）が混在した場合のソート安定性

**終了条件:**
- 10 連続実行で SARIF の SHA-256 ハッシュが一致
- 手動でソート順を検証するスクリプト（`jq` など）がパス

**タイムボックス:** 60 分  
**実施担当:** 実装者（実装後、CI 前）

---

### セッション 3 — 終了コード契約

**対象:** exit code `0/1/2` の正確な発火条件  
**テスト観点:**
- 違反ゼロの clean ソリューション → exit 0
- 意図的違反を含むサンプル → exit 1
- 存在しないパス → exit 2
- `.sln` はあるが `.csproj` の参照先が欠損 → exit 2（1 ではなく）
- MSBuildWorkspace ロード中の例外 → exit 2（未捕捉でプロセスクラッシュしないか）
- exit 1 のとき STDOUT が有効 SARIF か（findings を含む完全な出力があるか）

**終了条件:** 上記 6 ケースすべてで期待する exit code が得られること

**タイムボックス:** 45 分  
**実施担当:** 実装者

---

### セッション 4 — AGARCH0001 検出精度 / 誤検知

**対象:** レイヤー違反ルールのセマンティクス精度  
**テスト観点:**
- 禁止エッジ（`UI→Infrastructure`, `UI→Domain`, `Domain→Infrastructure`）が検出されるか
- 許可エッジ（`UI→Application`, `Application→Domain`）が誤検知されないか
- 依存種別ごとの検出:
  - 型の使用（フィールド宣言・ローカル変数）
  - メソッド呼び出し
  - 継承・インターフェース実装
  - 属性（`[FromServices(...)]` 等）
- テストプロジェクト（`*.Tests` 等）がルール対象外になっているか
- プロジェクト名からのレイヤー推論が曖昧なケース（例: `MyApp.UI.Tests`）

**終了条件:**
- 意図的違反サンプル 3 パターンが検出される
- 許可エッジで誤検知ゼロ
- テストプロジェクトが検出対象外

**タイムボックス:** 90 分  
**実施担当:** 実装者 + 別メンバー（クロスチェック）

---

### セッション 5 — AGCOMP0001 実コード構文カバレッジ

**対象:** 複雑度計算の実コードでの精度  
**テスト観点:**
- ユニットテストが未カバーの構文での計算値:
  - `switch` 式（C# 8+）: `case` ガード付きパターン
  - null 条件演算子 `?.`（分岐として数えるか？）
  - `??` / `??=` 演算子
  - ローカル関数・ネスト Lambda の複雑度をメソッドに含めるか
  - `is` パターン + `when` 節
- 閾値 15 ちょうどのメソッドが「違反なし」で報告されるか
- 閾値 16 のメソッドが「違反あり」で正しいメッセージ (`methodName`, `complexity`, `threshold` プロパティ含む) が出るか

**終了条件:** 上記各ケースの期待動作を仕様ドキュメント（`docs/rules.md`）と照合し、一致または不一致をバグ/仕様明確化として記録

**タイムボックス:** 60 分  
**実施担当:** 実装者

---

### セッション 6 — SARIF rules セクション完全性

**対象:** SARIF output の `tool.driver.rules` 配列の構造  
**テスト観点:**
- `shortDescription.text` / `fullDescription.text` が存在するか
- `helpUri` が設定されているか（またはオプションとして省略可か）
- `properties.category` が `"Architecture"` / `"Complexity"` 等で正しく設定されているか
- 同一 ruleId が 2 回以上 results に登場しても rules 配列に重複がないか（既存テストで確認済みだが実コードで再確認）
- `partialFingerprints` が存在する場合にその内容が決定論的か

**終了条件:** `docs/rules.md` 「SARIF 2.1.0 mapping rules」セクションの全フィールドが出力に存在すること

**タイムボックス:** 45 分  
**実施担当:** 実装者
